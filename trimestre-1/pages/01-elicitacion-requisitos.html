Introducción a la elicitación de requisitos

La elicitación de requisitos del software es la base fundamental de todo proyecto de desarrollo. El mundo empresarial se basa en la resolución de problemas, por lo que en el desarrollo de software es necesario definir un objeto de estudio para plantear qué se va a hacer y delimitar los tiempos estimados y costos.

Para resolver un problema, se debe buscar realmente qué es lo que se espera que solucione. Por ende, se debe hacer un levantamiento de información por medio de técnicas de recolección de datos.

Fuentes de la información

Es importante saber de dónde proviene la información:

  • Fuente primaria: Información obtenida directamente de la persona involucrada. Ejemplo: cuando alguien da su opinión de lo que observa.
  • Fuente secundaria: Información que llega por medio de otra persona. Ejemplo: cuando se presenta una situación y la información llega a través de una anécdota.
  • Fuente terciaria: Información que se conoce a partir de dos o más personas. Ejemplo: cuando se requieren varias opiniones de diferentes personas.

Técnicas de recolección de datos

Las técnicas de recolección de datos son la base principal del proyecto. Existen múltiples técnicas que permiten obtener información desde las fuentes primarias, siendo el cliente quien ofrece la información más confiable y real. Si se obtiene una buena recolección de datos, el proyecto tendrá una base sólida para su construcción.

Preguntas cerradas y abiertas

  • Preguntas cerradas: ofrecen opciones limitadas y predefinidas (sí/no, opción múltiple, escala). Facilitan el análisis cuantitativo y la tabulación de datos.
  • Preguntas abiertas: permiten respuestas propias del encuestado, útiles para explorar opiniones, experiencias y razones de fondo.

Entrevista

Es una conversación dirigida entre dos o más personas donde una, el entrevistador, formula preguntas para obtener información u opiniones del otro, el entrevistado. Las entrevistas son útiles cuando se necesita información flexible, dinámica y profunda.

Requisitos: preparación clara, duración definida, registro de información y un enfoque específico.

Ventajas

  • Interpersonales y flexibles.
  • Permiten aclaración inmediata.
  • Posibilitan observación directa del lenguaje corporal.

Desventajas

  • Se requiere mucho tiempo y recursos.
  • Existe subjetividad y sesgos.
  • No siempre hay sinceridad completa.
Ejemplo de entrevista para una app de gestión de tareas:

Un equipo quiere crear una aplicación enfocada en freelancers. Realiza entrevistas a diseñadores, programadores y redactores para entender sus dificultades con las herramientas actuales.

Encuesta y cuestionario

Una encuesta se usa generalmente para recoger datos de muchas personas en forma estructurada y rápida. Un cuestionario es la herramienta que contiene las preguntas de la encuesta y puede incluir preguntas abiertas o cerradas.

Encuesta

  • Más útil para obtener datos cuantitativos de gran volumen.
  • Permite identificar tendencias, porcentajes y frecuencias.

Cuestionario

  • Útil para profundizar en criterios, actitudes y percepciones.
  • Puede combinar preguntas cerradas y abiertas.

Taller de trabajo (Workshop)

Un taller es una actividad intensiva donde los participantes reciben información, comparten ideas y desarrollan capacidades en un corto tiempo. A menudo incluye dinámicas de grupo, lluvia de ideas, prototipado y resolución de problemas.

Actividad Duración
Introducción del proyecto y objetivos del taller 15 min
Mapa de empatía y perfil de usuario 30 min
Lluvia de ideas y priorización 60 min
Prototipado rápido 45 min

Observación

La observación consiste en estudiar el comportamiento real de las personas en su entorno natural o profesional. A través de ella se analizan procesos, necesidades y dificultades sin depender solo de opiniones expresadas verbalmente.

Prototipos

Un prototipo es una representación temprana del software o de una parte de la interfaz. Permite validar ideas antes de invertir mucho tiempo en desarrollo, y ayuda a detectar errores de diseño o de funcionalidad.

Historias de usuario

Las historias de usuario describen necesidades desde la perspectiva del usuario. Su formato típico es: “Como [usuario], quiero [objetivo], para [beneficio]”.

Ejemplo: “Como cliente, quiero registrar una compra online para pagar de forma rápida y segura.”

Requerimientos funcionales y no funcionales

Los requisitos funcionales describen lo que el sistema debe hacer; los requisitos no funcionales describen cómo debe comportarse o qué cualidades debe tener.

Requisitos funcionales

  • El sistema debe permitir iniciar sesión.
  • El sistema debe registrar clientes.
  • El sistema debe guardar ventas.
  • El sistema debe mostrar reportes.

Requisitos no funcionales

  • Debe funcionar en navegadores modernos.
  • Debe responder en menos de 3 segundos.
  • Debe ser fácil de usar para usuarios sin experiencia.
  • Debe proteger la información de usuarios y clientes.

Roles en el desarrollo de software

En un proyecto de software intervienen varias personas con funciones complementarias. Entre ellos están:

  • Cliente: expresa la necesidad o problema.
  • Analista: recoge, comprende y documenta los requisitos.
  • Diseñador: estructura la solución y la experiencia de usuario.
  • Desarrollador: construye la aplicación o sistema.
  • Tester o QA: valida que el sistema funcione correctamente.
  • Administrador de proyecto: coordina tiempos, tareas y recursos.

Diagramas de flujo generales (Flujogramas)

Un diagrama de flujo representa gráficamente los pasos que sigue un proceso. Se utiliza para comprender, analizar y documentar un procedimiento o sistema.

Sus símbolos más comunes incluyen:

  • Inicio y fin
  • Proceso
  • Decisión
  • Entrada/salida
  • Conector

Los flujogramas permiten identificar cuellos de botella, rutas repetitivas y decisiones clave dentro del sistema.

Diagramas de flujo de datos (DFD)

Los diagramas de flujo de datos muestran cómo circulan los datos dentro del sistema, desde las entidades externas hasta los procesos internos y los almacenes de información.

Notación Yourdon-Coad

Se caracteriza por representar procesos, entidades externas, almacenes de datos y flujos de información de forma clara y visual. Es útil cuando se busca explicar relaciones entre componentes del sistema.

Notación Gane-Sarson

Usa símbolos más estructurados y visualmente definidos para procesos, flujos y datos. Es especialmente apropiada para representar sistemas con lógica más formal o metódica.

Ejercicios de DFD

Los ejercicios de DFD permiten practicar la identificación de:

  • Entidades externas
  • Procesos principales
  • Almacenes de datos
  • Flujos de información

Ejemplo de proyecto sencillo: Panadería Estación Paisa

Un ejemplo práctico para entender la elicitación de requisitos es una panadería llamada Estación Paisa.

Se puede plantear el objetivo de desarrollar un sistema para registrar ventas, controlar inventario y generar reportes de producción. Con esta información, el analista puede identificar requisitos funcionales y no funcionales.

Requisitos funcionales posibles:
  • Registrar ventas por cliente.
  • Controlar el inventario de ingredientes.
  • Generar boletas o facturas.
  • Mostrar reportes del día.
Requisitos no funcionales posibles:
  • Velocidad de respuesta rápida.
  • Interfaz amigable para empleados.
  • Seguridad de los datos.
  • Compatibilidad con dispositivos de escritorio.

UML (Unified Modeling Language)

La UML es un lenguaje estándar para modelar sistemas de software. Permite representar clientes, procesos, datos y relaciones entre elementos mediante diagramas.

Algunos de sus diagramas más comunes son:

  • Diagramas de caso de uso: muestran interacciones entre usuarios y sistema.
  • Diagramas de clases: describen entidades y relaciones entre objetos.
  • Diagramas de secuencia: expresan el flujo temporal de mensajes.

En esta etapa inicial, el objetivo principal es comprender las necesidades reales del usuario y transformar esas necesidades en requisitos claros y verificables.
