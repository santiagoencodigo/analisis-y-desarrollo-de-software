01

Introducción a la elicitación de requisitos

La elicitación de requisitos del software es la base fundamental de todo proyecto de desarrollo. El mundo empresarial se basa en la resolución de problemas, por lo que en el desarrollo de software es necesario definir un objeto de estudio para plantear qué se va a hacer y delimitar los tiempos estimados y costos.

Para resolver un problema, se debe buscar realmente qué es lo que se espera que solucione. Por ende, se debe hacer un levantamiento de información por medio de técnicas de recolección de datos.

02

Fuentes de la información

Antes de recolectar datos, es clave saber de dónde proviene la información. Existen tres tipos de fuentes según su nivel de cercanía con la persona o situación que se investiga.

Fuente primaria

Información obtenida directamente de la persona involucrada.

Ejemplo: cuando alguien da su opinión de lo que observa.

Fuente secundaria

Información que llega por medio de otra persona.

Ejemplo: cuando la información llega a través de una anécdota.

Fuente terciaria

Información que se conoce a partir de dos o más personas.

Ejemplo: cuando se requieren varias opiniones de diferentes personas.
03

Técnicas de recolección de datos

Las técnicas de recolección de datos son la base principal del proyecto. Existen múltiples técnicas que permiten obtener información desde las fuentes primarias, siendo el cliente quien ofrece la información más confiable y real.

Preguntas cerradas y abiertas

Preguntas cerradas

  • Ofrecen opciones limitadas y predefinidas (sí/no, opción múltiple, escala).
  • Facilitan el análisis cuantitativo.
  • Permiten la tabulación rápida de datos.

Preguntas abiertas

  • Permiten al encuestado responder con sus propias palabras.
  • Útiles para explorar opiniones y experiencias.
  • Su análisis es más complejo pero más profundo.

Entrevista

Conversación dirigida entre dos o más personas donde el entrevistador formula preguntas para obtener información u opiniones del entrevistado. Son útiles cuando se necesita información flexible, dinámica y profunda.

Tipos de entrevista

  • No estructurada: libre y abierta, sin un plan determinado.
  • Focalizada: el entrevistador guía la conversación sin desviarse del tema.
  • Estructurada: preguntas específicas en un orden específico.
  • En escalera: las respuestas guían las siguientes preguntas para explorar motivos subconscientes.

Ventajas

  • Interpersonales y flexibles.
  • Aclaración inmediata de dudas.
  • Permite observar lenguaje corporal.
  • Alto nivel de participación del usuario.

Desventajas

  • Alto consumo de tiempo y recursos.
  • Riesgo de subjetividad y sesgos.
  • Posible falta de sinceridad.
  • Difícil generalización de resultados.
Ejemplo práctico Un equipo quiere crear una app para freelancers. Realiza entrevistas en profundidad con diseñadores, programadores y redactores para entender cómo organizan su trabajo, qué herramientas usan y qué problemas enfrentan.

Encuesta y cuestionario

Una encuesta recoge datos de muchas personas en forma estructurada y rápida. Un cuestionario es la herramienta que contiene las preguntas y puede incluir preguntas abiertas o cerradas.

Encuesta

  • Ideal para datos cuantitativos de gran volumen.
  • Identifica tendencias, porcentajes y frecuencias.
  • Permite comparar respuestas entre grupos.

Cuestionario

  • Útil para profundizar en criterios y percepciones.
  • Combina preguntas cerradas y abiertas.
  • Reduce el sesgo del investigador.
Ejemplo práctico El equipo crea un cuestionario online distribuido en redes sociales para conocer hábitos y preferencias de usuarios antes de diseñar la aplicación.

Taller de trabajo (Workshop)

Actividad intensiva donde los participantes comparten ideas y desarrollan capacidades en un corto tiempo. Incluye dinámicas de grupo, lluvia de ideas, prototipado y resolución de problemas.

Observación

Estudia el comportamiento real de las personas en su entorno natural o profesional. Permite analizar procesos, necesidades y dificultades sin depender solo de opiniones expresadas verbalmente.

Categorías de observación

Categoría Aspectos a observar
Comunicación Canales usados, comunicación entre áreas, incidencia en el resultado final, casos exitosos.
Sistema de información Procesos seguidos, principales inconvenientes en el manejo del sistema.

Prototipos

Representación temprana del software o de una parte de la interfaz. Permite validar ideas antes de invertir mucho tiempo en desarrollo, y ayuda a detectar errores de diseño o funcionalidad.

Ventajas

  • El cliente ve el sistema antes de desarrollarlo.
  • Se detectan confusiones antes de invertir tiempo.
  • Facilita el entendimiento entre cliente y desarrollador.

Desventajas

  • El cliente puede confundirlo con el producto final.
  • Crear y modificar prototipos requiere tiempo.
  • Demasiados cambios pueden retrasar el proyecto.

Historias de usuario

Describen necesidades desde la perspectiva del usuario final. Se escriben en lenguaje simple y sirven como requisitos funcionales para el equipo de desarrollo.

Formato: Como [usuario], quiero [objetivo], para [beneficio].

Ejemplos

  • Como usuario, quiero crear tareas con título, fecha y prioridad para organizar mis actividades.
  • Como usuario, quiero editar una tarea existente para actualizar la información.
  • Como usuario, quiero marcar tareas como completadas para tener control de lo que ya hice.
  • Como administrador, quiero gestionar múltiples usuarios para supervisar equipos de trabajo.
04

Requerimientos funcionales y no funcionales

Una vez recolectada la información, se debe definir qué necesita el software para funcionar. Los requisitos se clasifican en funcionales y no funcionales.

Requisitos funcionales

  • El sistema debe permitir iniciar sesión.
  • El sistema debe registrar clientes.
  • El sistema debe guardar ventas.
  • El sistema debe mostrar reportes.

Requisitos no funcionales

  • Debe funcionar en navegadores modernos.
  • Debe responder en menos de 3 segundos.
  • Debe ser fácil de usar para usuarios sin experiencia.
  • Debe proteger la información de usuarios.
05

Roles en el desarrollo de software

En un proyecto de software intervienen varias personas con funciones complementarias. Cada una aporta desde su especialidad.

ClienteExpresa la necesidad o problema.
AnalistaRecoge y documenta los requisitos.
DiseñadorEstructura la solución y la experiencia.
DesarrolladorConstruye la aplicación o sistema.
Tester / QAValida que el sistema funcione.
Project ManagerCoordina tiempos y recursos.
06

Diagramas de flujo generales (Flujogramas)

Un diagrama de flujo representa gráficamente los pasos que sigue un proceso. Se utiliza para comprender, analizar y documentar un procedimiento.

Símbolos principales

Símbolo Representación Significado
Inicio / Fin[●]Comienzo o final del proceso.
Actividad[   ]Tarea llevada a cabo durante el proceso.
Decisión◇Punto de bifurcación (sí/no).
Conexión→Dirección del flujo del proceso.
Documento📄Generación o consulta de un documento.
Envío de datos🖨️Envía datos a la impresora.
Muestra de datos🖥️Muestra datos en pantalla.

Reglas según estándar ISO

  • Escribir de arriba hacia abajo y/o de izquierda a derecha.
  • Usar solo líneas horizontales o verticales (nunca diagonales).
  • Evitar el cruce de líneas.
  • Solo los símbolos de decisión pueden tener múltiples salidas.
  • No deben quedar líneas de flujo sin conectar.
07

Diagramas de flujo de datos (DFD)

Los DFD muestran cómo circulan los datos dentro del sistema: desde las entidades externas hasta los procesos internos y los almacenes de información. A diferencia de los flujogramas, se centran en los datos, no en la secuencia.

Notación Yourdon-Coad

[ Cliente ] → ( Validar pedido ) → || Pedidos || ↓ ( Calcular total ) ↓ [ Cliente ] ← ( Facturar )

Niveles de DFD

Nivel Descripción
Nivel 0 (contexto)Sistema completo como un solo proceso.
Nivel 1Descompone el proceso principal en varios procesos.
Nivel 2 y superioresDescompone cada proceso de nivel 1 en subprocesos.

DFD vs. Flujograma

DFD Flujograma
Muestra el flujo de datos.Muestra la secuencia de pasos.
Se enfoca en el qué.Se enfoca en el cómo.
No tiene símbolos de decisión.Incluye rombos para condiciones.
Útil para análisis y diseño.Útil para programación y algoritmos.
08

Ejemplo: Panadería Estación Paisa

🎯 Objetivo del proyecto

Desarrollar un software para el control del personal en la panadería Estación Paisa en Terreros.

Objetivos específicos

  • Levantamiento de información: observación directa, entrevistas e historias de usuario.
  • DFD: representar el manejo de la información en el software.
  • UML: describir la estructura y comportamiento del sistema.
  • Requerimientos: definir requisitos funcionales y no funcionales.

Requisitos funcionales

  • Registrar ventas por cliente.
  • Controlar inventario de ingredientes.
  • Generar boletas o facturas.
  • Mostrar reportes del día.

Requisitos no funcionales

  • Velocidad de respuesta rápida.
  • Interfaz amigable para empleados.
  • Seguridad de los datos.
  • Compatibilidad con dispositivos de escritorio.
09

UML (Unified Modeling Language)

La UML es un lenguaje estándar para modelar sistemas de software. Permite representar clientes, procesos, datos y relaciones entre elementos mediante diagramas.

Diagramas más comunes

Casos de usoInteracciones entre usuarios y sistema.
ClasesEntidades y relaciones entre objetos.
SecuenciaFlujo temporal de mensajes.
ActividadesFlujo de trabajo de un proceso.
En esta etapa inicial, el objetivo principal es comprender las necesidades reales del usuario y transformar esas necesidades en requisitos claros y verificables.
