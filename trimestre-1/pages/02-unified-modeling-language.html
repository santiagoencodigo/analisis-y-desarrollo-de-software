UML y Metodologías de Desarrollo

El Lenguaje Unificado de Modelado (UML) es el estándar para especificar, visualizar y documentar sistemas de software. Junto con las metodologías ágiles como Scrum, XP y Kanban, conforman las herramientas esenciales para gestionar el ciclo de vida completo de un proyecto.

01 / FUNDAMENTOS

Lineamientos fundamentales del proyecto formativo

El diseño de un sistema de software educativo o productivo requiere una delimitación estricta del alcance para garantizar su viabilidad y éxito técnico.

Principio de simplicidad

El proyecto debe ser sencillo y tratar un único tema o línea de negocio centralizada.

Arquitectura centralizada

Un buen software se caracteriza por estar centralizado. Abarcar múltiples problemáticas dispersa el desarrollo.

Módulos base

Control de personal, control de inventario, gestión de citas. Cada uno representa una línea de negocio.

Formulación del objetivo general

Debe descomponerse en cuatro elementos indispensables:

Objetivo General = Verbo en Infinitivo + Elemento/Objeto + Empresa + Ubicación
Elemento Ejemplo
Verbo en infinitivoDesarrollar
Elemento o propósitocontrol de personal
Empresa o entidadpanadería La Paisa
Ubicación geográficaSoacha
Enunciado integrado: Desarrollar un software para el control de personal en la panadería La Paisa en Soacha.

Objetivos específicos

Representan el desglose fase por fase de las actividades necesarias:

  • Análisis: identificar, diagnosticar, estudiar.
  • Diseño: diseñar, planear, estructurar.
  • Desarrollo: desarrollar, construir, programar.
  • Pruebas: verificar, probar, validar.
  • Implantación: implementar, desplegar.
02 / PROCESO

Ingeniería de requisitos

La ingeniería de software abarca la obtención de los requerimientos, el diseño, la implementación, las pruebas, la instalación, el mantenimiento y la actualización del sistema. La ingeniería de requisitos se enfoca en la definición de lo que se desea producir.

Elicitar

Recolectar las necesidades de los stakeholders.

Analizar

Determinar viabilidad y consistencia de los requisitos.

Especificar

Documentar los requisitos de forma clara.

Validar

Verificar que reflejan lo que el cliente necesita.

Importancia: define qué debe hacer el sistema, alinea expectativas, evita desviaciones del alcance y permite rastrear cada requisito desde su origen hasta su implementación.
03 / ESTÁNDAR

Estándar UML

El Lenguaje de Modelado Unificado es la norma internacional para la especificación, visualización, construcción y documentación de los artefactos de un sistema de software.

Componentes esenciales de casos de uso

Actor

Entidad externa (rol de usuario, sistema externo o tiempo) que interactúa con el sistema. Se representa con un monigote.

Caso de uso

Bloque atómico de funcionalidad que aporta valor medible al actor. Se representa con un óvalo.

DFD vs. Casos de uso

DFD ≠ Diagrama de Casos de Uso
DFD (Diagrama de Flujo de Datos) Caso de Uso
Muestra cómo fluyen los datos: entradas, procesos, almacenamientos y salidas. Muestra la interacción entre actores y sistema desde la perspectiva del usuario.
Se enfoca en el qué datos se transforman. Se enfoca en el cómo interactúa el usuario con el sistema.

04 / DOCUMENTACIÓN

Historias de usuario

Una historia de usuario es una descripción corta y simple de una funcionalidad, escrita desde la perspectiva del usuario final.

Sintaxis:
Como <rol> quiero <acción> para poder <beneficio>

Estructura completa

Componente Descripción
HistoriaEnunciado principal con la sintaxis.
Puntos de historiaEstimación de complejidad (Planning Poker).
TareasActividades técnicas necesarias.
Pruebas de aceptaciónCriterios de completitud.
ResponsablesPersonas encargadas de la implementación.
SketchBoceto o prototipo de la interfaz.

Ejemplo: Inicio de sesión

Caso

Como usuario quiero iniciar sesión

Puntos de historia: 5

Tareas

  1. Crear la BD con tablas de usuarios y contraseñas.
  2. Crear el formulario de ingreso al sistema.
  3. Crear la plantilla de inicio de sesión.
  4. Generar la apertura de la BD.
  5. Generar el código de captura de usuario y contraseña.
  6. Generar los mensajes de error.
  7. Generar la llamada a la página principal tras ingreso exitoso.
  8. Validar ingreso por primera vez.
  9. Generar pantalla de cambio de clave.
  10. Guardar la nueva clave en la BD.

Pruebas de aceptación

  • Dejar los dos campos en blanco e intentar iniciar sesión.
  • Ingresar usuario y contraseña que no existan en la BD.
  • Ingresar usuario y contraseña válidos.
  • En el primer ingreso, solicitar cambio de contraseña.
05 / METODOLOGÍAS

Metodologías de desarrollo de software

01

Scrum

Marco de trabajo ágil que organiza proyectos complejos en ciclos cortos llamados sprints. Se basa en roles, artefactos y ceremonias.

Roles

Rol Responsabilidad
Product OwnerDefine y prioriza el Product Backlog.
Scrum MasterFacilita el proceso y elimina impedimentos.
Equipo de DesarrolloEquipo autoorganizado (3-9 personas).

Artefactos

Artefacto Descripción
Product BacklogLista priorizada de requisitos.
Sprint BacklogTareas seleccionadas para el sprint.
IncrementoVersión funcional y probada del producto.

Eventos

  • Sprint Planning: planificación del sprint.
  • Daily Scrum: reunión diaria de 15 minutos.
  • Sprint Review: revisión con stakeholders.
  • Sprint Retrospective: reflexión y mejora.
02

XP (eXtreme Programming)

Metodología ágil que enfatiza la calidad del código y la respuesta rápida a cambios.

Prácticas clave

  • Programación en parejas: dos desarrolladores, un código.
  • TDD (Test-Driven Development): pruebas antes del código.
  • Integración continua: integrar y probar frecuentemente.
  • Refactorización: mejorar sin cambiar comportamiento.
  • Propiedad colectiva: cualquiera puede modificar el código.
03

Kanban

Método para gestionar el trabajo mediante un flujo visual. Visualiza el trabajo en un tablero que muestra el estado de cada tarea.

Principios

  • Visualizar el flujo: usar un tablero Kanban.
  • Limitar el trabajo en progreso (WIP): controlar las tareas en cada estado.
  • Gestionar el flujo: eliminar cuellos de botella.
  • Mejora continua: optimizar según datos.

07 / PROTOTIPADO

Mapas de navegación y prototipado

Un mapa de navegación es una representación visual que muestra la estructura y las relaciones entre las diferentes pantallas o vistas de una aplicación.

Planificación visual

Visualiza la estructura completa de la interfaz.

Identificación de flujos

Detecta flujos de usuario complejos o redundantes.

Comunicación

Facilita el diálogo entre diseñadores, desarrolladores y stakeholders.

09 / REQUISITOS

Requisitos funcionales y no funcionales

La correcta definición de los requerimientos es el paso más importante para poder modelar y construir un DFD.

Requisitos funcionales

Qué debe hacer el sistema: operaciones, servicios y lógica de negocio.

"El sistema debe permitir iniciar sesión con usuario y contraseña."

Requisitos no funcionales

Cómo debe comportarse: rendimiento, seguridad, arquitectura, usabilidad.

"El inicio de sesión no debe tardar más de 2 segundos."

Analogía simple

Comprar un auto:

Requisito funcional:    "El auto debe tener frenos."          (Qué hace)
Requisito no funcional: "Deben detenerlo en <30m a 100km/h."  (Cómo lo hace)

Ejemplos en software

Requisito Funcional Requisito No Funcional
El sistema debe permitir registrar usuarios. Debe soportar 1.000 usuarios concurrentes.
El sistema debe generar reportes en PDF. Los reportes deben generarse en menos de 5 segundos.
El sistema debe enviar notificaciones por correo. Deben entregarse con un 99.9% de confiabilidad.
10 / FLUJO

Flujo metodológico del proyecto

Para iniciar el desarrollo del proyecto formativo, se ejecutan secuencialmente:

1

Elicitación de requisitos

Descubrimiento y recolección de necesidades. Se recopila material real: imágenes, facturas, documentos, videos.

2

Definición de objetivos

El objetivo general define el "qué"; los específicos desglosan el "cómo".

3

Especificación

"La columna vertebral del proyecto": define reglas, restricciones y funciones antes de escribir código.

4

Casos de uso e historias

Modelado funcional basado en el comportamiento observado del negocio.

Principio de diseño modular: cada clase o entidad del dominio debe corresponder a un módulo lógico o componente específico del sistema. Esto garantiza separación de responsabilidades, alta cohesión y bajo acoplamiento.
11 / CIERRE

Conclusión y líneas de investigación

Conclusiones

  • UML es el estándar para modelar sistemas de software, proporcionando un lenguaje común.
  • La ingeniería de requisitos es fundamental para garantizar que el software cumpla con las necesidades.
  • Las metodologías ágiles (Scrum, XP, Kanban) ofrecen enfoques flexibles y adaptativos.
  • Las historias de usuario y casos de uso capturan requisitos desde la perspectiva del usuario.
  • El proyecto formativo SENA sigue una estructura estandarizada que organiza el trabajo desde el problema hasta la implementación.
